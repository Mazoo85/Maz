# Maz — project guide for Claude

**Maz is the default game engine for this account.** When Cody asks to build a game — any game,
any genre — build it as a **Maz app** in this repo, on top of the existing engine. Do not reach for
Godot, Unity, a web-canvas one-off, or a from-scratch engine unless Cody explicitly asks for
something other than Maz.

## What Maz is

A native **C++20 + SDL3 + Vulkan** game engine — 2D-first but with a full 3D path — that has grown
to rough **Godot feature parity**. It is large and mostly **header-only**:

- **~690 headers** under `engine/include/maz/`, organized by subsystem:
  `math/` · `core/` · `game/` · `render/` · `physics` · `ecs/` · `anim/` · `audio/` · `ui/` ·
  `io/` · `net/` · `input/` · `platform/` · `scene/` · `script/` (a small scripting VM) · `fx/`.
- **~160 sample games and demos** under `apps/` — including full games: `pong`, `catcher`,
  `platformer`, `adventure`, `zomboid` (the flagship), `orbs`, `village`, `world`, `swarm`.
- **~370 tests** under `tests/`, and rich docs under `docs/`.

Because it's this large, **the first move for any new feature is to search `engine/include/maz/`
for what already exists** — reuse it, don't reinvent it. (There is already a `math::Geometry2D`,
a physics world, an audio DSP stack, an animation system, a UI toolkit, and much more.)

## Starting a new game — the workflow

```sh
tools/new-game.sh <name> ["Game Title"]     # e.g. tools/new-game.sh spacegame "Space Game"
```

This copies `apps/_template` (the canonical, mobile-ready starting point) to `apps/<name>`, renames
the build target to `<name>`, and registers it in the root `CMakeLists.txt`. Then:

```sh
cmake -S . -B build -G Ninja
cmake --build build --target <name>
./build/bin/<name>                          # add --headless --frames N to run with no window
```

Write the game in `apps/<name>/main.cpp`. Learn the shape of a game from:
- `docs/TUTORIAL_FIRST_GAME.md` — a guided "first game in 10 minutes".
- `apps/_template/main.cpp` — the mobile-ready loop (touch + keyboard unified, safe-area UI,
  auto-save on suspend, frame pacing, haptics).
- Existing full games — `apps/pong`, `apps/catcher`, `apps/platformer`, `apps/adventure` — for
  real patterns (input → sim → collision → render → HUD).

Each app's `CMakeLists.txt` is two lines: `add_executable(<name> main.cpp)` +
`target_link_libraries(<name> PRIVATE maz::maz maz_warnings)`.

## Building & testing

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure       # run headless with SDL_VIDEODRIVER=dummy
```

Full builds need the **Vulkan SDK loader + `glslang-tools`** and SDL's X11/Wayland/audio dev
packages (see `.github/workflows/ci.yml` for the exact apt list). SDL3 and GLM are fetched
automatically by CMake. The engine **degrades gracefully with no GPU/display**, so tests run
headless under the dummy SDL drivers.

## Conventions (match the existing code)

- **Strict warnings, `-Werror`**: `-Wall -Wextra -Wpedantic -Wshadow -Wconversion`. New code must
  compile clean under these (watch `-Wconversion` — cast narrowings explicitly).
- **Header-only + std/GLM where possible.** Keep game-logic types **testable with no GPU/window**
  (the whole `math`/`game` logic layer is). Math is GLM re-exported under `maz::math` with Vulkan
  conventions (depth 0..1, `ortho2D` top-left origin, +Y down).
- **Namespaces** mirror directories: `maz::math`, `maz::game`, `maz::render`, `maz::core`, …
- **Every new logic module gets a unit test** under `tests/`, registered in `tests/CMakeLists.txt`
  (`add_executable(...) + target_link_libraries(... maz::maz maz_warnings) + add_test(...)`).
- `docs/API.md` is generated by the `docsgen` tool during the build; if a build regenerates it,
  restore it (`git checkout -- docs/API.md`) before committing so it isn't churned.

## This environment (cloud box)

This session runs on a headless cloud box **without the Vulkan SDK / glslangValidator**, so a full
CMake build cannot run here. Verify header-only logic locally by compiling the relevant `tests/*`
file directly with `g++ -std=c++20 -Iengine/include -I<glm> <flags>` (clone GLM 1.0.1 to the
scratchpad for the headers); the **CI workflow does the full Vulkan build and the complete test
suite**. Never weaken CI or the renderer to make it build here — split GPU glue from pure logic and
verify the logic locally, the glue in CI.

## The arcade apps, and where the music comes from

Alongside the engine this repo carries the browser apps of MAZ ARCADE, listed in `shared/projects.js`.
Two of them are joined:

- **SCRIPT FORGE** (`film/`) — an idea becomes a screenplay, a reel, and a film.
- **SONG FORGE** (`music/`) — the AI music app: `composer.js` writes a song, `engine.js` plays it.

**The film's score is SONG FORGE's job, and must stay that way.** Do not write a second music
generator, and do not synthesise the score inside the film app. The division that already exists is
the one to keep:

- `film/js/film-score.js` (`FilmConductor`) turns a reel into a **score request** — genre, mood,
  seed, bpm chosen so bars land on the cuts, a section per scene, instruments following the tension
  — plus a **duck envelope** that keeps the music under the dialogue. Pure data; no audio in it.
- `music/js/composer.js` (`Composer.compose`) **composes** from that request, and
  `music/js/engine.js` (`Engine.Player`) **plays** it into a destination the film supplies.
- `film/js/film-audio.js` owns only what is not music: the character voices, the film's two buses,
  and the ducking.

So when the score is wanted somewhere new — the native renderer's soundtrack, an export, anything
else — the work is to give SONG FORGE a destination and let it compose, never to reimplement it.
Whatever composes a Maz film's music is SONG FORGE.
